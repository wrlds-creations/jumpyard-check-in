# Decisions

This file is the source of truth for meaningful project decisions. Add entries when a choice affects architecture, scope, cost, data ownership, security, deployment, UX direction, or future maintainability.

## Decision Log

| ID | Date | Decision | Rationale | Impact | Revisit Trigger |
|---|---|---|---|---|---|
| `D0001` | 2026-05-18 | Frontend must not call Roller directly in production architecture. | Roller credentials must not be exposed in frontend. A server-side layer is needed for logging, retries, error handling, and controlled fallbacks. JumpYard Cloud/server API will own pilot operational state. | Production architecture uses `check-in app -> JumpYard Cloud/server API -> Roller API`. Frontend work must target server-owned contracts rather than Roller directly. | Revisit only if Roller provides a credential-safe frontend integration model and WRLDS explicitly approves an architecture change. |
| `D0002` | 2026-05-18 | Roller integration must fail closed unless configured for Playground. | Sprint 1 starts against Roller Playground only. The integration should reject missing environment config, non-playground environments, and production/live-looking URLs before any Roller client can be used. | Roller validation blocks unsafe config early and keeps production credentials or endpoints out of local/dev validation. | Revisit when production Roller integration is explicitly scoped and approved. |
| `D0003` | 2026-05-19 | Each ticket should use a dedicated `codex/` branch and `main` should change only through a review/merge step. | Ticket branches keep scope clear, make commits reviewable, and reduce the risk of mixing unrelated local changes into project history. A local commit should not be treated as a `main` update. | Codex creates or switches to a ticket branch before ticket work, stages only ticket files, commits only when explicitly requested, and never pushes directly to `main`. | Revisit only if the WRLDS workflow or repository release process changes. |
| `D0004` | 2026-05-19 | JumpYard Cloud should be built as the AWS server-side boundary for phone check-in flows. | The project needs server-side Roller credentials, token reuse, rate-limit control, idempotency, audit logging, normalized responses, and JumpYard-owned pilot state. | Future implementation should target API Gateway/Lambda, Secrets Manager, Aurora PostgreSQL, S3 raw payload storage, CloudWatch, SQS/EventBridge, and a rate-limit control mechanism before phone UI calls Roller-backed operations. | Revisit only if WRLDS chooses a non-AWS hosting model. |
| `D0005` | 2026-05-19 | Booking lookup should use `GET /bookings/{uniqueId or bookingReference}` as the primary live lookup path. | Roller response v3 confirms Get Detail of a Booking is authoritative for live existing-booking lookup. Playground also accepted booking reference `5001370` at `/bookings/5001370`. | JumpYard Cloud lookup contract should normalize booking detail and use `GET /bookings` search only as fallback when a guest lacks QR/code. | Revisit if Roller changes endpoint behavior or booking references stop resolving through the detail path. |
| `D0006` | 2026-05-19 | Check-in should be modeled as ticket-level redemption, not a booking-level checked-in flag. | Roller documentation and process work identify `POST /redemptions` as the supported check-in action, operating on ticket ids. | JumpYard Cloud must resolve booking references to ticket ids before redeeming and must store internal check-in attempts/audit separately from Roller ticket state. | Revisit if Roller provides a confirmed booking-level self-service check-in API. |
| `D0007` | 2026-05-19 | Existing-booking add-products should create a separate linked add-on booking for the pilot. | Same-booking update plus Roller payment link can send the guest to a separate hosted payment page where return to the JumpYard PWA/check-in flow is not reliable enough for the pilot. A separate add-on booking lets JumpYard keep the PWA flow coherent and link the original booking to the add-on booking in JumpYard Cloud. | JumpYard Cloud should create and store a link between original booking and add-on booking. Same-booking `PUT /bookings/{uniqueId}` plus payment link is deferred, not the primary pilot path. | Revisit only if Roller confirms a reliable payment-link return path and JumpYard explicitly chooses same-booking update UX. |
| `D0008` | 2026-05-19 | JumpYard Cloud should store minimal operational state and Roller ids, not full Roller-owned data. | Roller remains source of truth for bookings, products, payments, and ticket redemption. JumpYard needs audit, handoff, idempotency, and short-lived normalized state without unnecessary PII. | Aurora PostgreSQL should hold Roller snapshot tables, operational state, check-in attempts, handoff sessions, idempotency records, product cache metadata, webhook events, and event logs. | Revisit when compliance or reporting requirements require longer retention or richer local data. |
| `D0009` | 2026-05-19 | JumpYard Cloud should maintain a local booking index from daily Data API seed, booking webhooks, and live REST confirmation. | Morning seed reduces peak-time dependency on live Roller calls, webhooks keep same-day changes fresh, and live lookup confirms check-in-critical state. Roller still remains source of truth. | Future implementation should add a BookingIndex and BookingSeedRun model, webhook idempotency, and reconciliation logic before relying on the phone flow at pilot scale. | Revisit if Roller Data API or webhook access is unavailable for the pilot. |
| `D0010` | 2026-05-19 | Playground test bookings should be created by an internal seed tool, not by a public demo button in the phone check-in flow. | Test-data creation needs fake names/products/statuses without polluting guest UX or normal production flows. A protected server-side seed tool can encode Roller-required booking fields once and stay Playground-only. | Future implementation should add a Playground-only seed script or protected admin action that creates deterministic fake bookings through JumpYard Cloud. | Revisit if Roller provides a better native Playground fixture/reset mechanism. |
| `D0011` | 2026-05-19 | JumpYard Cloud infrastructure should start as a deploy-blocked AWS CDK TypeScript foundation. | The project needs a scalable AWS shape before endpoint implementation, but real AWS creation must wait until account, region, owner, data classification, exportability, and cost metadata are confirmed. | T0004 adds CDK definitions and local synth validation only. Deploys remain blocked until WRLDS metadata and AWS account preflight are completed. | Revisit when first dev deploy metadata is confirmed. |
| `D0012` | 2026-05-19 | Booking index ingestion should use daily seed, booking webhook, and live REST refresh as separate responsibilities. | Data API seed is good for a baseline, webhooks catch same-day changes without polling, and live REST detail is still needed before check-in-critical decisions. Separating the paths keeps the phone flow fast without treating local data as truth. | Future implementation should build separate seed run tracking, webhook intake/enrichment, freshness labels, and live refresh logic. Get attendance must not seed expected guests. | Revisit if Roller Data API or webhook access is not available in the pilot environment. |
| `D0013` | 2026-05-19 | The first real AWS dev deploy should happen immediately after T0005, before schema, seed tooling, and endpoint implementation. | T0004 created the CDK foundation and T0005 defines the ingestion contract. Deploying dev next gives the team a real API/database environment to build against instead of designing more implementation in the abstract. | T0006 should confirm WRLDS metadata and deploy the CDK foundation to dev. T0007 should add Aurora schema/migrations, followed by deterministic Playground seed tooling and lookup implementation. | Revisit if AWS metadata is unavailable or the user chooses to continue local-only development. |
| `D0014` | 2026-05-19 | JumpYard Cloud dev Aurora should use `aurora-postgresql` engine version `16.13` in `eu-north-1`. | The first T0006 deploy attempt failed because AWS RDS in `eu-north-1` does not offer Aurora PostgreSQL `16.3`; AWS reported `16.13` as an available PostgreSQL 16 version. | CDK must synthesize the dev cluster with `16.13` so the deploy can complete in the confirmed WRLDS dev region. | Revisit when upgrading Aurora PostgreSQL or changing AWS region. |
| `D0015` | 2026-05-20 | Aurora schema changes must run through versioned SQL migrations tracked in `jumpyard.schema_migrations`. | Backend tickets need a repeatable database state across dev, staging, and production without manual console edits. A migration table makes applied changes auditable and prevents duplicate execution. | `infra/migrations/` owns SQL migrations, and `infra/scripts/run-migrations.ts` applies them through the Aurora Data API for the approved environment. | Revisit if the project adopts a managed migration framework or changes database platform. |
| `D0016` | 2026-05-20 | Roller Playground seed writes must be explicit, guarded, and based on child/variation product IDs. | Roller create-booking payloads require product variation IDs, and test-data writes must never accidentally target Live. A dry-run-first command with a separate write confirmation makes the seed path useful without weakening the Playground guard. | T0008 seed tooling reads products first, generates deterministic booking payloads, blocks Live/production URLs, and writes only when `--apply` plus `ROLLER_SEED_ALLOW_WRITE=I_UNDERSTAND_THIS_WRITES_PLAYGROUND_BOOKINGS` are both present. | Revisit if Roller provides a native fixture/reset mechanism or if seed creation moves behind an authenticated admin API. |
| `D0017` | 2026-05-20 | The first lookup endpoint should use live Roller booking detail before Aurora index lookup exists. | T0009 needs a real phone-flow lookup before daily seed and webhook ingestion are implemented. Roller remains the booking source of truth, and live detail is the safest first deployed behavior. | `POST /v1/check-in/lookup` reads Secrets Manager/SSM config server-side, calls Roller `GET /bookings/{identifier}`, enriches product names from `/products`, and returns a normalized JumpYard response without raw Roller payloads. Aurora persistence and local-index-first lookup remain future tickets. | Revisit after daily seed and webhook ingestion populate the Aurora booking index. |
| `D0018` | 2026-05-20 | Phone booking lookup should show both ready and unpaid found bookings, but only ready bookings can start check-in. | Unpaid bookings are valid bookings and should be visible to the guest, but the flow must not continue into safety/redeem before payment handling exists. The frontend should consume JumpYard Cloud eligibility rather than duplicate Roller rules. | T0010 maps `ready` to booking summary with an active check-in CTA, maps `payment_required` to booking summary with `Obetald` and a blocked CTA, and keeps stop states for `wrong_date`, `no_redeemable_tickets`, not-found, and service failures. | Revisit when payment and staff-assisted recovery flows are implemented. |

## Active Constraints

| Constraint | Source | Impact | Revisit Trigger |
|---|---|---|---|
| Roller is the source of truth for bookings. | Sprint 1 project context | Booking validation must reconcile with Roller. | Revisit if JumpYard chooses another booking system. |
| JumpYard Cloud/server API owns pilot operational state. | Sprint 1 project context | Safety status, handoff code, and session status should not be owned by the frontend. | Revisit after pilot state model is finalized. |
| Roller config must be Playground-only for Sprint 1. | D0002 | Roller client creation fails unless `ROLLER_ENV=playground` and base URL is clearly Playground. | Revisit when production Roller integration is approved. |
| Work one scoped ticket at a time. | WRLDS Codex workflow | Prevents implementation scope from expanding into future tickets. | Revisit only if workflow changes. |
| Use one dedicated branch per ticket. | D0003 | Keeps ticket changes isolated from `main` and from unrelated local user changes. | Revisit only if workflow changes. |
| JumpYard Cloud is the server-side integration boundary. | D0004 | Phone app work should target JumpYard Cloud contracts rather than Roller contracts. | Revisit only if architecture changes. |
| Check-in is ticket-level redemption. | D0006 | Redeem flows must resolve and operate on ticket ids. | Revisit if Roller API changes. |
| Booking index is operational cache, not source of truth. | D0009 | Seed/webhook data can speed up lookup, but live Roller state still governs check-in writes. | Revisit if data ownership changes. |
| AWS deploys require target identity preflight. | D0011/T0006 | Future `cdk deploy` runs must verify AWS account, region, environment, and WRLDS tags before changing resources. | Revisit only if deployment automation replaces local deploys. |
| Attendance is not expected-guest seed data. | D0012 | Attendance/redeem data can reconcile actual arrivals, but the morning booking index should come from bookings, tickets, payments, and customers. | Revisit only if Roller changes Data API semantics. |
| AWS dev is the implementation target after T0006. | D0013 | Future backend tickets should build against the deployed dev API/database foundation. | Revisit if dev resources are removed or replaced. |
| Aurora engine versions must match the target AWS region. | D0014 | CDK deploys should use an RDS engine version confirmed in the region, not just a generally valid Aurora version. | Revisit when upgrading database engine or changing region. |
| Aurora schema changes use versioned migrations. | D0015 | Database changes should be reviewed, committed, and applied by migration command rather than edited manually in AWS. | Revisit if migration tooling changes. |
| Playground seed writes require explicit confirmation. | D0016 | Test bookings can be useful, but writes stay local-tool-only, Playground-only, and dry-run-first. | Revisit if seed creation moves to an authenticated admin API. |
| Lookup uses live Roller detail until the booking index exists. | D0017 | T0009 can support phone lookup without pretending Aurora already has seeded booking data. | Revisit after T0011/T0012 ingestion work. |
| Phone lookup only starts check-in on ready eligibility. | D0018 | Phone UI may show unpaid bookings, but should block check-in until future payment flows handle them. Wrong-date, non-redeemable, and failed lookups still stop in lookup. | Revisit when payment and redeem flows are implemented. |
